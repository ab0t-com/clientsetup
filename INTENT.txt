Auth Mesh Client Setup Kit
==========================

PURPOSE
-------
This is the canonical, self-contained setup package for any service ("client")
that integrates with the Auth Mesh authentication platform.

A new client copies this directory, edits three config files, runs the CLI,
and has a fully working auth integration. Users can sign up, log in, and
access the service. No custom code. No ongoing maintenance.


AUDIENCE
--------
- Service teams building on Auth Mesh (external companies or internal teams)
- DevOps engineers setting up new service deployments
- Platform team maintaining the standard onboarding flow


ARCHITECTURE: WHY IT WORKS
---------------------------
Auth Mesh uses Google Zanzibar (relation-based access control) under the hood.
Permissions are NOT granted per-user. They flow through organizational
hierarchy:

    Service Org (platform_service)
      └── End-Users Org (child, parent_id = service org)
            ├── parent relationship → Zanzibar inheritance
            ├── hosted login configured HERE
            ├── default_role = "member"
            ├── User A (member) → permissions inherited from org
            └── User B (member) → permissions inherited from org

When you create a child org with parent_id, the auth server writes:
    organization:{child}#parent@org:{parent}

This Zanzibar relationship means permission checks on the child org can walk
up to the parent. Users who are members of the child org inherit the
service's permissions through this chain.

This is zero-config, zero-maintenance by design:
  - No per-user permission grants
  - No callbacks or webhooks to handle new signups
  - No cron jobs to backfill permissions
  - No service-side middleware to detect and fix missing permissions
  - Membership in the org IS the permission grant

Revoking access is equally simple — remove the user from the org.


ORG STRUCTURES (end_users.org_structure)
----------------------------------------
The default end-users pool (above) suits services where users are interchangeable
consumers of a shared API. But some services treat each user as a tenant with
their own private space — their own API keys, their own teammates, their own
billable usage. Think GitHub user namespaces, Notion personal workspaces, or
Vercel personal scopes.

For those services, set:

    end_users.org_structure.pattern = "workspace-per-user"

The auth service's built-in event handler then materializes a private nested
org for each new user on registration:

    Service Org (yourservice)
      └── End-Users Org
            ├── Default Users team  (existing behavior preserved)
            └── alice's workspace   (settings.type = "user_workspace", owner = alice)
                  ├── Default team  (with default_grant permissions)
                  └── alice (owner + team member)

The workspace is an org. Alice owns it. She can invite teammates, create more
teams inside it, manage settings — all using existing org / team / permission
APIs. Bob (a different signed-up user) cannot see or touch Alice's workspace.

WHY this is shipped as a built-in pattern (not client-side code):
  - Every per-user product wants this same shape. Universal patterns belong in
    the platform, not duplicated in 12 client services.
  - Setup is one config field. Auth handles the rest.
  - The handler runs in-process inside the auth service — no external service
    to deploy, no webhook subscription to maintain, no failure mode to handle.
  - Workspaces are orgs. Nothing about the data model changes. All existing
    tooling (audit logs, hierarchy queries) just works.

WHAT'S COMING (not in this release):
  - "enterprise-on-billing-tier"  — auto-create enterprise org on tier upgrade
  - "workspace-plus-enterprise"   — combines per-user workspace + enterprise path

The org_structure.pattern enum grows additively. Existing client configs never
break when new patterns are added.


WHAT'S IN HERE
--------------
release/                        The shipped tool — one static `authsetup` binary
  authsetup-linux-amd64         Prebuilt binaries (no runtime deps)
  authsetup-linux-arm64
  authsetup-darwin-amd64
  authsetup-darwin-arm64
  checksums.txt                 SHA-256 checksums
  VERSION                       Release version

install.sh                      One-line installer (curl | sh) — fetches the right binary

config/                         Input configuration (edit these)
  permissions.json.example      Service permission schema reference
  oauth-client.json.example     OAuth client config reference
  hosted-login.json.example     Login page branding / registration rules reference
  org-structure.json.example    End-users org structure (flat / workspace-per-user)
  api-consumers.json.example    API consumers reference
  archetypes/                   Per-service-type config presets
  clients.d/                    One JSON per upstream provider you consume

schema/                         JSON Schemas for every config + credential file
docs/                           Client-facing docs (USAGE.md, CLI.md, MIGRATION.md)
skills/                         Agent skills (auth-mesh-setup, authsetup-cli, …)
llms.txt                        Machine-readable orientation for coding agents

INTENT.txt                      This file
README.md                       Client-facing documentation

Credentials are NOT written into this directory. Every command writes generated
secrets (service org + admin creds + API key, OAuth client_id, end-users org,
login URL) to ~/.authmesh/<service>/ (mode 0600), outside any repo, alongside a
redacted journal. The `credentials/*.example` files here are schema references
for those outputs only.


DESIGN PRINCIPLES
-----------------
ZERO-CONFIG:    Users get permissions from org membership, not per-user grants
ZERO-MAINTENANCE: No cron, no callbacks, no middleware — it just works
IDEMPOTENT:     Every command reconciles config against live state; safe to re-run
ORDERED:        Steps are numbered (run 01 … run 08); each may depend on prior outputs
SELF-CONTAINED: One static binary — `curl` to install; no runtime deps (no jq/python/bash)
ENVIRONMENT-AWARE: AUTH_SERVICE_URL switches between prod/dev/local
CONFIG-DRIVEN:  All service-specific values live in config/ JSON files
CREDENTIALS-SEPARATE: Secrets go to ~/.authmesh/<service>/ (0600, outside any repo)
SCHEMA-DOCUMENTED: .example files + schema/ show exact input/output contracts
STANDARD:       Same binary works for ANY service — just change the config
